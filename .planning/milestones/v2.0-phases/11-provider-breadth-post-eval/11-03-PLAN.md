Decision (call this out and honor): **Option A — narrow the capability to Photoroom's actual single-subject contract.** Justification:
- Photoroom's public Image Editing API (https://image-api.photoroom.com/v2/edit) accepts ONE `imageFile` subject plus documented edit fields (`removeBackground`, `outputSize`, `padding`, `shadow.mode`, `background.color`, `background.prompt`, etc.). It does not accept a multi-layer composition list. CR-02 line 156 confirms our `imageGenMcp.layers` field is silently dropped.
- D-04 locks Photoroom as a "specialized product/image editing provider for extract_subject and product-photography composition behavior" — single-subject product photography with shadow/relighting is exactly what the Image Editing API delivers.
- D-15 explicitly says shadow/background quality measurement happens "where the Image Editing API is used." Single subject is enough.
- PROV-01 (with shadow) is delivered through Photoroom's shadow/relighting on the subject, not through a multi-layer compositor we'd have to build locally first (Option B).
- Keeps Phase 11 within scope budget — no new sharp pre-composition pipeline, no new fixtures, no new scorers.

Out of scope (deferred per planner instructions): WR-01 (Ideogram fetch timeout) and WR-02 (fal queue poll per-request abort) are warnings only and do NOT block the phase goal. They are noted in `<deferred>` for a follow-up.

Output: A narrowed Photoroom composite adapter, a corrected eval case, an eval-time contract lint, regression tests, and updated README docs that unblock live human verification.
