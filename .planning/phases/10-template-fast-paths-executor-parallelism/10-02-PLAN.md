    **Refactor strategy (preserves topological correctness):**

    Replace the current `while (ready.length > 0) { ... }` loop. Extract the per-node processing (everything inside the loop body that handles ONE node) into an `async function processNode(nodeId: string): Promise<void>` that:
    1. Resolves refs (with try/catch → error path)
    2. Looks up capability (with not-registered → error path)
    3. Validates params (with try/catch → error path)
    4. Calls `runNodeWithRetry`
    5. On success: writes artifact, sets outcome, pushes downstream nodes whose indegree reaches 0 onto a SHARED `ready` array
    6. On failure: sets outcome to error, calls `skipDownstream`

    Then replace the outer loop with:
    ```typescript
    import { MAX_PARALLEL_NODES } from './sharp-config.js';
    // ...
    while (ready.length > 0) {
      // Drain up to MAX_PARALLEL_NODES nodes from the ready queue at once.
      const batch: string[] = [];
      while (batch.length < MAX_PARALLEL_NODES && ready.length > 0) {
        const id = ready.shift()!;
        if (outcomes.has(id)) continue; // already handled (skip/error)
        batch.push(id);
      }
      if (batch.length === 0) break;
      // Run batch in parallel; each processNode independently mutates outcomes,
      // traceNodes, skips, indegree, and ready. Promise.all awaits all to settle.
      await Promise.all(batch.map((id) => processNode(id)));
    }
    ```

    **Critical invariants to preserve:**
    - `outcomes`, `traceNodes`, `skips`, `indegree`, `ready`, and `nodeById` are all single-threaded data structures. Node.js's single-threaded event loop guarantees that JavaScript code in `processNode` runs without interleaving except at `await` boundaries. The mutations to these maps occur synchronously after the `await runNodeWithRetry()` resolves. THIS IS SAFE — no locks needed.
    - `buildResolveCtx(inputs, outcomes)` is called at the START of `processNode` for THIS node. Snapshot semantics: a node sees the outcomes that exist at the moment IT begins resolving refs. Because parents of a node only finish before this node enters the ready queue (indegree decremented to 0 only after parent succeeds), this is correct — a node's parent outputs are always visible by the time this node is in the batch.
    - Topological order is preserved by indegree: a node enters `ready` ONLY when all its parents have completed successfully. Parallelism happens between SIBLINGS (no dependency edge), never between a node and its ancestor.
    - When a node fails and `skipDownstream` is called, it marks outcomes for descendants. If a descendant was already in the current `batch` and is in-flight when its parent fails — that cannot happen, because the descendant could not have been added to `ready` until the parent's `processNode` succeeded.
    - When a node fails, it does NOT cancel siblings in the same batch. Siblings complete normally (this is correct behavior: they have no dependency on the failed node).

    **Add a guard against duplicate scheduling:**
    Inside `processNode`, before any work, check `if (outcomes.has(nodeId)) return;` — defensive against a node being skipped (by a parent failure in another concurrent processNode) between when it was added to `ready` and when its turn in the batch comes up.
